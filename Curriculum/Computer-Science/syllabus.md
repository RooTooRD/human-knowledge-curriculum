# Computer Science Syllabus

| Unit | Prerequisites | Ordered lessons | Observable outcomes | Common misconception | Mastery checks |
|---|---|---|---|---|---|
| `CSC-B01` Information, representation, bits, data, and abstraction | `FND-B08`, `MAT-B02` | 1. Information and encoding; 2. bits, binary, hex; 3. numbers, text, image, audio representation; 4. compression/error; 5. abstraction layers | Encode/decode common data; calculate size/range; explain abstraction loss | Bits have no inherent meaning without an encoding | ☐ Convert representations; ☐ trace one artifact through layers |
| `CSC-B02` Algorithms, state, control flow, and problem solving | `CSC-B01`, `LOG-B02` | 1. Problem specification; 2. sequence, state, assignment; 3. condition and iteration; 4. decomposition and pseudocode; 5. trace and termination | Design and trace algorithms; identify state/invariants; argue termination for simple loops | Code is an implementation of an algorithm, not the algorithm itself | ☐ Write pseudocode for new tasks; ☐ trace and debug by hand |
| `CSC-B03` Programming fundamentals | `CSC-B02`, `MAT-B06` | 1. Values, types, expressions; 2. functions and scope; 3. conditionals/loops; 4. strings/collections; 5. I/O, errors, tests | Implement small programs; decompose into functions; test edge cases | Passing examples do not prove correctness | ☐ Build a tested command-line program; ☐ explain every state change |
| `CSC-B04` Files, structured data, command line, version control, debugging | `CSC-B03`, `FND-B08` | 1. Paths, streams, permissions; 2. shell navigation/pipelines; 3. CSV/JSON and parsing; 4. commits, branches, merges; 5. debugger, logs, minimal reproduction | Manipulate data/files safely; use version history; debug systematically | Version control is not backup by itself, and random edits are not debugging | ☐ Complete a branch/merge workflow; ☐ diagnose a seeded defect |
| `CSC-I01` Data structures and complexity | `CSC-B03`, `MAT-I01` | 1. ADTs and invariants; 2. arrays/lists/stacks/queues; 3. trees/heaps/hash tables; 4. graphs; 5. asymptotic time/space and amortization | Implement/select structures; analyze operations; preserve invariants | Big-O is growth class, not exact runtime | ☐ Implement core structures; ☐ justify choices and complexity |
| `CSC-I02` Core algorithms | `CSC-I01`, `STA-B03` | 1. Search/sort/select; 2. traversal and shortest paths; 3. spanning/flow orientation; 4. string/numeric algorithms; 5. randomized algorithms | Implement and prove core algorithms; compare complexity; test edge cases | Faster asymptotics need not win at every input size | ☐ Implement a graph/string suite; ☐ prove correctness and bounds |
| `CSC-I03` Algorithm design | `CSC-I01`, `MAT-I08` | 1. Divide-and-conquer; 2. greedy and exchange proofs; 3. dynamic programming; 4. backtracking/branch-bound; 5. reductions and approximation | Recognize design patterns; derive recurrences; prove correctness | Dynamic programming is not merely recursion with a cache | ☐ Solve unseen problems with three paradigms; ☐ write proofs and bounds |
| `CSC-I04` Automata, languages, computability, and complexity | `CSC-I01`, `LOG-I03` | 1. Regular languages/finite automata; 2. grammars/pushdown automata; 3. Turing machines; 4. decidability/reductions; 5. P, NP, NP-completeness orientation | Construct automata/grammars; prove nonregularity/undecidability; perform reductions | NP means verifiable nondeterministically, not “not polynomial” | ☐ Solve automata/language tasks; ☐ give a valid undecidability reduction |
| `CSC-I05` Computer architecture | `CSC-B01`, `PHY-B04` | 1. Boolean logic and circuits; 2. data path/control and ISA; 3. assembly and calling convention; 4. memory hierarchy/cache; 5. I/O, pipelining, parallelism | Trace instruction execution; write small assembly; analyze cache/performance | Clock rate alone does not determine performance | ☐ Trace a program to gates/memory; ☐ optimize measured bottleneck |
| `CSC-I06` Operating systems | `CSC-I05`, `CSC-I01` | 1. Kernel, syscall, privilege; 2. process/thread/scheduling; 3. synchronization/deadlock; 4. virtual memory; 5. filesystems, devices, isolation | Write concurrent code; reason about races/deadlocks; explain virtual resources | Concurrency is not identical to parallel execution | ☐ Implement synchronized service; ☐ diagnose OS resource failure |
| `CSC-A01` Parallel, concurrent, and distributed computing | `CSC-I06`, `CSC-I02` | 1. Parallel decomposition and models; 2. locks, actors, lock-free orientation; 3. communication and clocks; 4. consensus/replication/failure; 5. scalability and consistency | Design concurrent/distributed algorithms; reason under failures; measure scaling | Distributed failures are partial, and network communication is not reliable/instantaneous | ☐ Build a fault-tested distributed component; ☐ state consistency guarantees |
| `CSC-I07` Networks and the Internet | `CSC-B04`, `CSC-I05` | 1. Signals, packets, layering; 2. link/IP, addressing, routing; 3. TCP/UDP/congestion; 4. DNS, HTTP, TLS; 5. wireless, measurement, governance | Trace a web request; subnet/route; capture/analyze traffic; explain reliability/security layers | The Internet and Web are not the same, and packet delivery is best-effort | ☐ Diagnose a network trace; ☐ implement a protocol client/server |
| `CSC-I08` Databases | `CSC-B04`, `MAT-B08` | 1. Conceptual/relational modeling; 2. algebra and SQL; 3. normalization/constraints; 4. indexes/query plans; 5. transactions/isolation/recovery | Design schemas; write/optimize queries; reason about concurrency | A database is more than stored tables, and indexes accelerate reads with costs | ☐ Build/query a normalized DB; ☐ reproduce and fix an anomaly |
| `CSC-A02` Distributed data, streaming, warehouses, and retrieval | `CSC-I08`, `CSC-A01` | 1. Partitioning/replication; 2. consistency and distributed transactions; 3. batch/stream processing; 4. warehouse/lake/OLAP; 5. indexing, ranking, retrieval | Architect data platforms; select consistency model; build streaming/retrieval pipeline | “Exactly once” depends on defined boundaries and idempotence | ☐ Implement resilient pipeline; ☐ defend architecture trade-offs |
| `CSC-I09` Programming languages | `CSC-I04`, `CSC-I05` | 1. Syntax/semantics; 2. scope, binding, closures; 3. types and polymorphism; 4. functional, object, logic, concurrent paradigms; 5. compilation/runtime/GC | Compare paradigms; reason about types/evaluation; implement interpreter fragments | Language syntax does not define its computational model alone | ☐ Build a typed mini-interpreter; ☐ translate solution across paradigms |
| `CSC-I10` Software engineering | `CSC-B04`, `WRT-I02` | 1. Requirements/stakeholders; 2. modular design/APIs; 3. testing and review; 4. teamwork/version/release; 5. maintenance, debt, lifecycle | Elicit requirements; design/test maintainable software; collaborate through change | Agile does not mean no planning/documentation | ☐ Deliver team software with tests/docs; ☐ conduct requirements-to-release trace |
| `CSC-A03` Architecture, reliability, observability, performance, and operations | `CSC-I06`, `CSC-I07`, `CSC-I10` | 1. Architectural styles/interfaces; 2. SLOs, redundancy, degradation; 3. logs/metrics/traces; 4. profiling/capacity; 5. deployment, incident, postmortem | Design operable systems; diagnose from telemetry; improve reliability empirically | Redundancy without independent failure modes may not increase reliability | ☐ Run load/failure exercises; ☐ produce blameless corrective postmortem |
| `CSC-I11` HCI, accessibility, graphics, and interactive systems | `CSC-B03`, `PSY-B02` | 1. Users, tasks, context; 2. perception/action and interaction principles; 3. prototyping/usability studies; 4. accessibility and inclusive design; 5. graphics/event loops/interfaces | Prototype/test interfaces; remediate accessibility; interpret usability evidence | User preference alone is not usability, and accessibility is not an optional polish | ☐ Complete tested accessible prototype; ☐ document findings and revisions |
| `CSC-A04` Compilers, virtual machines, and language implementation | `CSC-I09`, `CSC-I06` | 1. Lexing/parsing; 2. AST, types, semantic analysis; 3. IR/optimization; 4. code generation/linking; 5. VM, JIT, runtime/GC | Build a compiler pipeline; implement analyses; reason about runtime trade-offs | Compilers do more than translate source line by line | ☐ Compile a small language; ☐ validate semantics and optimization |
| `CSC-A05` Graphics, vision, robotics, embedded, and specialized platforms | `CSC-I02`, `MAT-I06`, `ENG-I04` | 1. Geometric transformations/rendering; 2. image formation/features; 3. perception/estimation; 4. sensing, planning, control; 5. real-time/embedded constraints | Implement perception/render/control components; integrate hardware/software under timing limits | Simulation success does not guarantee physical-world robustness | ☐ Build one embodied/visual system; ☐ test latency, noise, failure |
| `CSC-A06` Social, ethical, environmental, and professional computing | `CSC-I10`, `PHI-I05`, `ECO-I03` | 1. Stakeholders and power; 2. privacy/security/fairness; 3. labor, access, and platforms; 4. energy/material lifecycle; 5. professional duty and governance | Conduct impact assessment; identify externalities; make defensible professional decisions | Technical neutrality does not erase design choices or distributional effects | ☐ Audit a system's lifecycle impacts; ☐ defend a mitigation/governance plan |
| `CSC-E01` Computer science research frontiers | `CSC-A01`, `CSC-A03`, `CSC-A04` | 1. Frontier mapping and literature; 2. formal/empirical/systems questions; 3. benchmark and baseline design; 4. artifact/evaluation; 5. reproducibility and publication | Formulate original CS research; build and evaluate an artifact/theory; report reproducibly | Benchmark improvement without validity or generality is not sufficient contribution | ☐ Produce publishable research artifact; ☐ pass technical defense and replication |
